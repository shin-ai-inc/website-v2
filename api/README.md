# ShinAI サポートAI（チャットボットAPI）

公開サイトのチャットに応答する Cloudflare Worker。
知識源は公開サイト16ページの本文のみで、機密は一切含まない。

## 設計の要点

**なぜ全文投入をやめたか（実測による設計変更）。**
当初はサイト全文（約14,000字）をそのままシステムプロンプトへ積んでいた。
容量には収まるが、モデルは埋もれた事実を拾えず、「商号は」という問いにすら
「資料にない」と答えた。**渡せることと、見つけられることは別である。**
関係するチャンクだけを選ぶ方式に変えたところ、同じ質問群が全て正答するようになり、
プロンプトは 15,206字 → 平均1,804字（8.4分の1）に縮んだ。精度と費用が同時に改善した。

**なぜハイブリッド検索か。**
字面一致だけでは「料金」と「費用」、「御社の名前」と「商号」が繋がらない。
逆に埋め込みだけでは固有名詞やサイト固有語（七つのShin等）を取り落とす。
両方を走らせ、順位融合（RRF）で束ねる。RRFは尺度合わせの調整項を持たないため、
コーパスが変わっても壊れない。

**なぜベクトルDBを立てないか。**
チャンクは約120件。全件との内積は1ミリ秒に満たない。埋め込みはビルド時に確定し
int8量子化して同梱するので、実行時に要るのは質問1件分の変換だけ。
外部DBは鍵・同期ずれ・障害点・費用を増やすだけで、この規模では何も速くしない。
将来チャンクが数千件を超えたら、`api/lib/retrieve.mjs` だけを差し替えればよい
（`index.mjs` は選定結果しか見ない）。

**なぜチャンクをHTML構造から切るか。**
FAQは `<details>`、会社概要は `<dl>` と、意味の境界が既にマークアップされている。
`_build/chunk.mjs` がそれを読むので、FAQ台帳を手で持つ必要がなく、
サイト本体と乖離しようがない。会社概要の事実カードだけは `pin` を付け、
質問の内容によらず常に同梱する（最も問われ、かつ最も短い）。

**なぜ知識をビルドで生成するか。**
手書きのFAQを別に持つと、必ずサイト本体と乖離し、AIが古い事実を配る。
`_build/build.mjs` が公開HTMLの `<main>` から毎回作り直すので、
サイトを直せば知識も自動で追従する。公開HTMLからの抽出なので、
機密が混入する経路が構造的に存在しない。

**防御の重心。**
知識が公開情報のみである以上、最大の実害は情報漏洩ではない。
「当社が言っていないことを当社の口から言わせる」ことと「OpenAI口座の踏み台化」である。
よって入力の検閲より、出力の統制と支出の上限を厚くしている。

**なぜ応対を「禁止の列挙」で作らないか。**
振る舞いを直すたびに禁止事項を足した結果、規範は26項目・2,200字まで膨らんだ。
知識（約1,800字）より指示のほうが長い状態である。そして守られなくなった。
これは全文投入でモデルが事実を見つけられなくなったのと同じ構造で、
項目が増えるほど互いに注意を薄める。
禁止を減らし、望ましい応対を六つの実例で示す形へ変えた（`lib/guard.mjs` の応対の例）。
規範は1,467字・15項目になり、遵守はむしろ上がった。

**なぜ後処理を残すか。**
規範に書いても消えない癖がある（末尾の問い返しは二度書いても残った）。
生成物の体裁を、指示の遵守だけに賭けない。実例で大半を防ぎ、
残りを `sanitizeAnswer` で確定的に落とす。

## 多層の統制

| 層 | 実装 | 止めるもの |
|---|---|---|
| 受理契約 | `lib/contract.mjs` | `model`・`messages` 等の注入による汎用LLMプロキシ化 |
| 根拠の限定 | `lib/retrieve.mjs` | 質問に関係しない記述をそもそもモデルへ見せない |
| 入力分類 | `lib/guard.mjs` | 典型的なプロンプトインジェクション |
| 構造分離 | `index.mjs` | 知識は system、入力は user。連結しないことで指示への昇格を防ぐ |
| 話題スコープ | `lib/guard.mjs` のシステムプロンプト | 資料に根拠のない事柄（競合評価・法律相談・時事）を一括で抑止 |
| 日次予算 | `lib/budget.mjs` + Durable Object | 低速分散攻撃による課金枯渇 |
| 出力ゲート | `lib/outgate.mjs` | 金額・納期・保証の約束生成 |

クライアント側（`scripts/chatbot.js`）にも同種の検証があるが、あれは
体験のための早期フィードバックであり統制ではない（curlで迂回される）。
サーバ側が最終防壁。

## 初回セットアップ

```bash
# 1. 知識ベースを生成（api/knowledge.*.json ができる）
#    OPENAI_API_KEY を渡すと埋め込みも計算して同梱する（ハイブリッド検索が有効になる）。
#    鍵が無ければベクトルなしで生成され、字面検索のみで動作する（ビルドは止まらない）。
OPENAI_API_KEY=$(cat 鍵を書いたファイル) node _build/build.mjs

# 2. Cloudflare へログイン
cd api && npx wrangler login

# 3. 秘密を投入（コードにも設定ファイルにも書かない）
npx wrangler secret put OPENAI_API_KEY
npx wrangler secret put IP_SALT        # 任意の長いランダム文字列

# 4. デプロイ
npx wrangler deploy
```

### OpenAI 側で必ず行うこと

コード側の上限は実装が正しい限り効くが、設定ミスや想定外の経路では効かない。
**コードの正しさに依存しない最終防壁**を口座側に置く。

1. このボット専用の **OpenAI プロジェクト**を作る（他事業と口座を混ぜない）
2. そのプロジェクトに**月次のハードリミット**を設定する
3. プロジェクトスコープの鍵を発行し、上の `wrangler secret put` に使う

## 日次上限の考え方

`wrangler.toml` の `DAILY_LIMIT` は次から導出している。

```
許容月額 1,500円（約$10）÷ 30日 = 1日あたり約$0.33
1リクエスト約$0.0004（入力約1,200＋出力300トークン＋質問の埋め込み）
→ 約800件/日
```

検索で根拠を絞る前は1件あたり約$0.0015で、上限は300件だった。
埋もれを直した結果として、費用も4分の1になっている。

上限に達したら OpenAI を呼ばず、問い合わせフォームへ穏やかに誘導する
（エラーにしない）。公開後1週間の実測で見直すこと。変数化してあるので
`wrangler.toml` を書き換えて再デプロイするだけでよい。

## 検証

```bash
node --test tests/*.test.mjs   # 全92件（外部依存なし・決定的）
python tools/audit_replies.py  # 公開中のAPIへ18問を投げ、機械が書いた徴候を検出
```

応対の自然さは単体テストで固定できない（生成であり毎回異なる）。
一方で癖そのものは機械的に判定できる。目視で確認していた頃は、
一つ直すたびに別の癖が生まれることを繰り返した。
`tools/audit_replies.py` は名乗りの差し込み・社名の連呼・内部の言い方・
今いるサイトへの誘導・型どおりの締め・定型の受けとめ・絵文字・Markdown・
息継ぎの読点・人物の代名詞を検出する。規範や検索を変えたら公開前に実行する
（OpenAIを呼ぶため課金される。CIには置かない）。

| ファイル | 対象 |
|---|---|
| `tests/api-contract.test.mjs` | 受理契約 |
| `tests/worker.test.mjs` | 入出力ガード |
| `tests/budget.test.mjs` | 予算・出力ゲート |
| `tests/chunk.test.mjs` | HTMLからの分割（構造の保存） |
| `tests/retrieve.test.mjs` | 字面検索・pin・順位 |
| `tests/vector.test.mjs` | 量子化・コサイン・順位融合 |
| `tests/knowledge.test.mjs` | 生成物と実データでの検索精度 |

## 変えてはいけないこと

- **ストリーミング応答を導入しない。** 表示済みのトークンは取り消せず、
  出力ゲートが原理的に機能しなくなる。タイプライター表示は
  クライアント側の演出で足りている（`chatbot.js`）。
- **受理するフィールドを増やさない。** 増やすときは脅威を再評価する。
- **システムプロンプトに未公開情報を入れない。** ここは秘密を置く場所ではない。
- **知識源に外部データ（RSS・外部URL・会話ログ）を混ぜない。**
  混ぜた瞬間、間接プロンプトインジェクションが実在の脅威に変わる。
- **知識を全文投入する設計へ戻さない。** 一度そうして失敗している。
  容量に収まることは、モデルが事実を見つけられることを意味しない。
- **チャンクを大きくしない。** 埋もれは長さから生まれる。
  `tests/knowledge.test.mjs` が1,200字の上限を機械で守っている。
- **規範に禁止事項を足し続けない。** 一度26項目まで膨らませて失敗している。
  振る舞いを変えたいときは、まず応対の例を直すか差し替える。

## ベクトル検索の運用

2026-08-12 に有効化した。監査ログの `dense: true` が、その応答でベクトル側が
使われたことを示す。字面のみへ縮退していれば `false` になる。

**サイトの文章を直したら、鍵を渡して再生成すること。**
渡し忘れるとベクトルなしで生成され、検索は静かに字面だけへ落ちる（一度そうなった）。
ビルドは警告を出すが、見落とさないこと。

```powershell
$env:OPENAI_API_KEY = Read-Host "OpenAI APIキー"; node _build/build.mjs
cd api; npx wrangler deploy; cd ..; Remove-Item Env:OPENAI_API_KEY
```

有効化で繋がるようになった例。いずれも文字の重なりが無く、字面検索では届かない。

| 訪問者の言葉 | 資料側の言葉 |
|---|---|
| ノウハウが人に貼り付いている | 暗黙知 |
| 機密データを外に出したくない | オンプレミス対応 |
| 納期 | 期間 |
| pricing | cost |
| on-premises | no data leaves your walls |

`lib/retrieve.mjs` の `QUERY_SYNONYMS` は、ベクトルが無い間の代替として置いた。
いまは埋め込みが同じ役割を果たすため、増やす理由はない。
